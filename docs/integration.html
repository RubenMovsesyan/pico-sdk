Integration guide

How to use this SDK in your own Pico project, assuming your project also builds with buildcpp rather than CMake or Bazel.

Flashable images are possible — from the consumer side

This SDK builds to a plain static library — no linker script, no boot_stage2 build, no UF2 conversion inside this repo's own build.cpp (see Scope & exclusions). That's deliberate: this repo's job is "compile the SDK as a library", not "produce firmware". But everything a consumer needs to go the rest of the way is already vendored in this tree — the real linker-script fragments (src/rp2_common/pico_standard_link/script_include/, src/rp2040/pico_platform/), the real boot2 sources and pad_checksum tool (src/rp2040/boot_stage2/) — none of it needs to be written from scratch. See Producing a flashable image below for the three gotchas that aren't obvious from just reading the source.

1. Add it as a submodule

git submodule add git@github.com:RubenMovsesyan/pico-sdk.git external/pico-sdk
git submodule add git@github.com:RubenMovsesyan/buildcpp.git external/buildcpp

(Adjust paths to match your project's layout — this SDK's own fork lives at tools/external/pico-sdk relative to tools/buildcpp, for reference.)

2. Build the SDK

cd external/pico-sdk
clang++ -std=c++23 build.cpp -o build   # first time only — self-rebuilds after
./build                                  # rp2040, static (what you want for firmware)

This produces external/pico-sdk/.build/rp2040/lib/libpico_sdk_rp2040.a plus the generated headers under external/pico-sdk/.build/rp2040/generated/pico_base/.

3. Wire it into your own build.cpp

Your project needs the same cross-compile flags as the SDK itself (they have to match — different --target/--sysroot/-march between your objects and the library you're linking against will not work), plus -I for every SDK component header directory your code actually #includes, plus a link against the built archive: 

#include "../buildcpp/build.hpp"

int main(int argc, char** argv) {
    initLog(4096);

    Build build(".build", "clang++", argc, argv);

    BuildGroup& app = build.addGroup();
    app.setCompiler("clang");   // same reasoning as the SDK itself: `restrict` etc.
                                  // break under clang++'s forced C++ mode

    app.addCompileFlag("--target=armv6m-none-eabi");
    app.addCompileFlag("-mfloat-abi=soft");
    app.addCompileFlag("-march=armv6m");
    app.addCompileFlag("--sysroot=/path/to/arm-gnu-toolchain/arm-none-eabi");

    // Same defines the SDK itself was built with — see platforms/rp2040.html.
    app.addCompileFlag("-DPICO_BOARD=\\\"pico\\\"");
    app.addCompileFlag("-DPICO_RP2040=1");
    app.addCompileFlag("-DPICO_32BIT=1");
    app.addCompileFlag("-DPICO_ON_DEVICE=1");
    app.addCompileFlag("-DPICO_NO_HARDWARE=0");
    app.addCompileFlag("-DPICO_BUILD=1");

    // Only the component include dirs your code actually uses — not the whole tree.
    app.addInclude(Include<Direct>("external/pico-sdk/src/rp2_common/pico_stdlib/include"));
    app.addInclude(Include<Direct>("external/pico-sdk/src/rp2_common/hardware_gpio/include"));
    app.addInclude(Include<Direct>("external/pico-sdk/src/rp2_common/hardware_uart/include"));
    app.addInclude(Include<Direct>("external/pico-sdk/src/common/pico_base_headers/include"));
    app.addInclude(Include<Direct>("external/pico-sdk/src/boards/include"));
    app.addInclude(Include<Direct>("external/pico-sdk/.build/rp2040/generated/pico_base"));
    // ...and so on for every other component header dir you touch. There's no single
    // umbrella include dir — each component publishes its own, same as the SDK's own
    // build.cpp discovers them.

    app.addLink(Link<Path>("pico_sdk_rp2040", "external/pico-sdk/.build/rp2040/lib"));

    Task& main_obj = app.addTask(Object("src/main.c"));
    app.addTask(Binary("firmware"), {main_obj});

    build.build();
    return 0;
}

Working out which include dirs you need

There's no consolidated umbrella header. If you're not sure which component a given #include lives under, grep the SDK for it: 

grep -rl "gpio_put" external/pico-sdk/src/rp2_common/*/include

or just look at compile_commands.json in external/pico-sdk/ after building it — every -I flag the SDK's own build used is right there for any file you're pulling functions from.

Testing your app against host too

If your app's logic doesn't depend on real peripheral behavior, you can build and run it natively the same way: point your include dirs at external/pico-sdk/src/host/*/include instead of rp2_common/rp2040, drop every cross-compile flag (no --target/--sysroot/-march), match the host defines from Host, and link against external/pico-sdk/.build/host/lib/libpico_sdk_host.a instead. See Host for what is and isn't real in that build.

Producing a flashable image

Getting from "links against libpico_sdk_rp2040.a" to "runs when you power on the board" needs three more pieces, none of which live in this repo's own build.cpp — they're consumer-side, built directly from files already in this tree. Verified end-to-end against a real Pico; each of the three failure modes below was hit and diagnosed the hard way, so they're recorded here rather than rediscovered next time.

1. Link the real linker-script chain — watch the -L order

src/rp2040/pico_platform/memmap_default.ld is upstream's real, usable entry point (just INCLUDE "memmap_default.incl") — the whole .incl chain under src/rp2_common/pico_standard_link/script_include/ and src/rp2040/pico_platform/script_include/ uses ld's native INCLUDE "file" directive, resolved via -L search paths, no CMake templating required. Two gotchas:

  • set_memory_locations.incl references RAM_ORIGIN_DEFAULT etc. but nothing in the chain INCLUDEs the file that defines them (rp2040/pico_platform/script_include/default_locations.ld) — upstream's CMake passes it as a second -T/--script= alongside the main one. Chain the two yourself (e.g. a two-line wrapper script that INCLUDEs both by full path).
  • rp2040/pico_platform/script_include must come before pico_standard_link/script_include in -L order. Both directories contain a file named sections_default_text.incl — the pico_standard_link one is generic, the rp2040 one is an intentional override ("RP2040 binaries must begin with boot2"). ld resolves a bare-filename INCLUDE via the first -L dir that has it. Get the order backwards and the link still succeeds cleanly — but .boot2 ends up placed after .text instead of at flash offset 0, where the bootrom unconditionally expects it. Verify placement with arm-none-eabi-objdump -h, not by reading the script text.

Also needs pico_flash_region.ld generated from pico_standard_link/pico_flash_region.template.ld (substitute ${PICO_FLASH_SIZE_BYTES_STRING} — 2MB for Pico/Pico W) and, if hardware_psram is in your include closure at all, pico_psram_region.ld the same way from its own template (zero-length is the correct stub when there's no PSRAM).

2. Force pico_runtime_init's object into the link

pico_runtime_init/runtime_init.c registers every init step (runtime_init_early_resets — which clears RESETS for IO_BANK0/PADS_BANK0, without which GPIO writes are silent no-ops — plus clocks, post-clock resets, spin locks, …) purely by placing a function pointer in a .preinit_array.<priority> linker section. Nothing calls them by name. Upstream's CMake builds this as an INTERFACE library — its sources compile directly into your target, so they're never subject to lazy archive extraction. A single flat libpico_sdk_rp2040.a doesn't have that property: normal archive extraction only pulls a member when something references a symbol it defines, and every function in runtime_init.c is __weak — a weak-only match doesn't satisfy that rule either. Net effect: the object silently never gets linked in, runtime_init()'s init-array is empty, and nothing looks broken until you check with arm-none-eabi-nm/objdump.

Fix: force it with -Wl,-u,runtime_init_install_ram_vector_table — the one non-__weak symbol in that file. Pulling it in via -u (a real, strong-symbol match) brings every other registration in the same translation unit along as a side effect, regardless of which symbol triggered the extraction. (--whole-archive also "works" but pulls in pico_malloc's __wrap_malloc/etc too — an opt-in heap-debugging feature normally enabled via CMake's -Wl,--wrap=malloc — and fails to link on the missing __real_* symbols --wrap would otherwise synthesize.)

3. boot2's checksum seed is 0xffffffff, not pad_checksum's default

src/rp2040/boot_stage2/pad_checksum ifile.bin ofile.S defaults to seed 0 when run bare. Upstream's boot_stage2/CMakeLists.txt always invokes it as pad_checksum -s 0xffffffff .... Different seed, different checksum — and the RP2040 bootrom's own validation is a fixed algorithm expecting the 0xffffffff-seeded value specifically. Get this wrong and the bootrom silently refuses to execute boot2 at all. This is the most dangerous gotcha of the three: it looks identical to "nothing is flashed" or "the board is dead" — no LED, no measurable power draw beyond the bootrom's own idle polling — regardless of whether every other piece (linker script, boot2 placement, runtime_init) is already correct. If a build compiles, links, and flashes via picotool without error but the board does nothing at all on both a fresh flash and a real (non-BOOTSEL) power cycle, check this first.

Flashing

picotool (a real, standard Raspberry Pi tool, not something built from this SDK) does the rest: picotool uf2 convert app.elf -t elf app.uf2 -t uf2 for a portable drag-and-drop image, or picotool load -x app.elf -t elf to flash and immediately run over USB while the board is in BOOTSEL mode — no manual UF2 step needed for that path. -x performs a real bootrom reboot (the same boot path as a cold power-on, not a debugger-style entry-point jump), so it's a faithful test of the real boot sequence.
